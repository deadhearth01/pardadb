Smart data masking for banks

Each role sees only what it needs.The data never changes.

PardaDB sits between your staff and the bank’s SQL databases. It finds personal data by itself (card numbers, Aadhaar, PAN, phone numbers, names, balances) and hides it the moment a query runs, based on who is asking. Nothing is copied. Nothing is rewritten.

01 The problem

Inside a bank, too many people can read every customer’s secrets.

A normal database shows everyone everything. A support agent who only needs the last four digits of a card sees the whole number. An analyst who only needs age groups sees birthdays, names and balances.

Today’s fixes break. Masked copies of the database go stale and double the storage. Hand-written views miss new columns. And nobody can prove afterwards who looked at what.

What each person actually needs

  • AdminReal values, for fixing problems. Fully audited.
  • SupportEnough to recognise a caller: first name, last four digits.
  • AnalystPatterns, not people: tokens, age bands, balance ranges.

PardaDB gives each of them exactly that, from the same live tables, with no copy to keep in sync.

02 How it works

Four steps. No changes to your data.

Point PardaDB at a database. It does the rest on its own, and you can check every decision it made.

  1. Step 01

    Scan

    Reads a small sample from every column and recognises personal data by its shape, its checksum and the column name.

    129,260 rows · ~0.5 s
  2. Step 02

    Tag

    Gives each column a label such as high-risk ID or financial, with the evidence shown next to it.

    PII_HIGH · PII_MEDIUM · FINANCIAL_CONFIDENTIAL
  3. Step 03

    Mask

    When someone runs a query, the answer is masked for their role on its way out. The stored data is never touched.

    policy.json: tag × role → rule
  4. Step 04

    Prove

    Every query is written to a tamper-evident log, and fingerprints show the tables are exactly as they were.

    hash-chained audit · SHA‑256

03 What you get

Everything a bank needs to share data safely.

Finds PII by itself

Cards (Luhn-checked), Aadhaar, PAN, SSN, phones, email, UPI, names, addresses, balances.

Masks per role

Full, partial, token, range or redacted, decided per column and role at query time.

Inference guard

Stops queries that try to work out hidden values by filtering or sorting on them.

Read-only by design

Every write to bank data is blocked. Databases are opened read-only.

Tamper-evident audit

Each query record carries the hash of the one before. Edit one and the chain breaks.

Integrity proof

SHA-256 fingerprints before and after show the tables did not change.

Free text and JSON

Masks PII inside support tickets, notes and JSON fields, not just whole columns.

Three databases, one result

SQLite, MySQL and PostgreSQL through one interface, with identical output.

05 Safety

Hard to trick. Impossible to change. Easy to prove.

Masking the output is not enough if someone can guess the hidden value with clever questions. PardaDB checks every query before it runs, and fails closed.

Try to cheat the guard

Masking the answer is not enough if a clever question can work out the hidden value. Pick a trick and watch what PardaDB says.

pardadb guardBLOCKED
support> SELECT * FROM cards WHERE CARD_NO LIKE '4111%';
BLOCKED inference guard: role 'support' cannot filter on cards.card_no (PII_HIGH); that would reveal masked values

# Matching the first digits would leak digits Support may not see.

Read-only

PardaDB can never change bank data. Databases are opened read-only, and every write statement is refused before it reaches them, even for Admin.

admin> UPDATE accounts SET curr_bal = 0;

Audit chain

Every query is recorded: who, which role, what SQL, what was masked. Each record stores the fingerprint (hash) of the record before it. Try quietly editing an old one.

06 Built for long-run use

Made to stay on for months.

PardaDB is one small process that runs next to your databases all day. Everything that could grow is capped, and anything that breaks heals itself.

  • Bounded memory. The event list is capped at 200, the AI result cache at 20,000 entries and query results at 1,000 rows.
  • Scan cost stays flat. Scans sample 200 values per column, so the cost does not grow with table size.
  • Small footprint. ~60 MB RAM for the engine and web app with three databases, ~0% CPU when idle.
  • Self-healing. An unreachable database is retried every 10 s; the schema is re-checked every 30 s and new columns are re-scanned automatically.
  • Stable tokens across restarts. The HMAC key is persisted, so analytics keep working day after day.
  • Fails closed. Anything the guard cannot analyse is refused.
  • Safe with many users at once: one lock per database connection, and a dropped connection is reopened and the query retried once.
  • The audit log rotates by size and the hash chain continues across files, so it can run for years and still be verified.

07 Optional AI

Rules catch patterns. A small AI model catches names.

08 For developers

One command to start. A plain REST API to build on.

A single Python process. Use the web dashboard, the full-screen terminal UI, the pardadb CLI, or call the API from your own tools.

Install in one command

All options: README
bash 
curl -fsSL https://raw.githubusercontent.com/deadhearth01/pardadb/main/FULL_CODE/scripts/install.sh | bash

With the problem pack and the AI model:

curl -fsSL https://raw.githubusercontent.com/deadhearth01/pardadb/main/FULL_CODE/scripts/install.sh | bash -s -- --data /path/to/B1_Smart_Data_Masking_PII --with-ai
  1. Run the command for your system.
  2. Put the problem pack in FULL_CODE/data (or pass it with --data).
  3. Start it: cd ~/pardadb/FULL_CODE && uv run pardadb opens http://127.0.0.1:8765.

From a clone:

git clone https://github.com/deadhearth01/pardadb && ./pardadb/FULL_CODE/scripts/install.sh

Needs git and Python 3.10+. The installer checks both and tells you what to install.

quick start · shell
# connect, scan, open dashboard + terminal UI
$ pardadb
# scan once and print the PII catalog
$ pardadb scan --db mysql
# run a query as a role
$ pardadb query --role support --sql "SELECT * FROM cards LIMIT 5"
# same query, all three roles side by side
$ pardadb compare --sql "SELECT cust_nm, mob_no FROM customers"
# SHA-256 proof that nothing changed
$ pardadb verify --db postgres
REST · curl
# health, backends and scan progress
$ curl -s localhost:8765/api/status

# run a masked query as a role (or "user")
$ curl -s -X POST localhost:8765/api/query \
    -H 'Content-Type: application/json' \
    -d '{"sql":"SELECT card_no FROM cards LIMIT 3","role":"support"}'

# the same SQL for admin, support and analyst
$ curl -s -X POST localhost:8765/api/compare \
    -d '{"sql":"SELECT cust_nm FROM customers LIMIT 3"}'
